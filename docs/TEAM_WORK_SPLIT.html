01 — Project Overview

What we are building

A QR-based ATM authentication layer. It plugs into an existing bank's ATM and an existing bank's mobile app. It allows a customer to unlock the ATM cash-withdrawal flow without inserting a physical card — the customer scans the ATM's QR with their bank app, approves with their existing biometrics, and the ATM unlocks.

Our system does not move money, hold balances, talk to the bank's ledger, or replace ATM hardware. It only answers one question on demand: "is this customer authorised for this ATM session right now?"

The three components

+---------------------------+ +-------------------------+ | ATM Simulator | | Mobile Bank App | | (Web — React) | | (React Native/Expo) | | shows menu, QR, unlock | | scans QR, approves | +-------------+-------------+ +------------+------------+ | REST + WebSocket | REST | | v v +-------------------------------------------------------------+ | Authenticator — Auth Middleware (Go) | | session create · JWT QR · approve · expire · audit log | +-------------------------------------------------------------+
The team split, in one line. You own the two simulation surfaces — the ATM screen and the bank-app mockup. Your teammate owns the authenticator — the brain of the product. The two halves meet at a documented HTTP + WebSocket contract on localhost:4000.
02 — Team Split at a Glance

Who owns what

YOU — Simulation Engineer

ATM Simulator + Bank App Mockup

All user-facing surfaces. The ATM screen the customer sees, and the bank-app feature the customer uses to approve. Calls the authenticator's APIs over HTTP and listens on WebSocket for instant unlock.

Stack

  • ATM Simulator: React + Vite + TypeScript
  • Mobile mockup: React Native + Expo
  • Camera: expo-camera
  • QR rendering: qrcode.react
TEAMMATE — Authenticator Engineer

Auth Middleware Backend

The brain. Issues short-lived signed QR tokens, validates approvals from the bank app, pushes the unlock signal back to the ATM over WebSocket, and writes an audit log for every state change.

Stack

  • Runtime: Go 1.22 + net/http
  • Real-time: gorilla/websocket
  • Signing: golang-jwt/v5 (HS256)
  • Session store: in-memory sync.RWMutex map (Redis-ready)

Why this split works

  • Parallel work, zero blocking. Once the API contract on the next page is agreed, the two tracks can build independently with mocks and meet at the end.
  • Clear ownership boundary. No shared files, no merge conflicts.
  • Demo-able in isolation. Each track can demo its own piece to Sir before integration.
03 — Integration Contract

The API that joins the two tracks

This is the single document both engineers must obey. If you both implement against this contract correctly, integration is a five-minute job.

HTTP endpoints (served by the Authenticator)

Verb · PathCallerPurpose
POST /api/sessionATM SimulatorCreate a new ATM session. Returns sessionId, qrToken, expiresAt.
GET /api/session/:idATM SimulatorPolling fallback if WebSocket is not available.
POST /api/session/approveMobile AppBody: { qrToken, deviceId, customerRef }. Verifies and marks session approved.
POST /api/session/:id/consumeATM SimulatorCalled after the ATM hands control to the existing withdrawal flow.
GET /api/auditEitherDev-only audit log dump.
GET /api/healthEitherHealth check.

WebSocket channel

ATM Simulator connects to ws://localhost:4000/ws?sid={sessionId} right after creating a session. The Authenticator pushes:

  • { "type": "subscribed", "sid": "…" } on connect
  • { "type": "approved", "session": { … } } when the bank app approves
  • { "type": "consumed", "session": { … } } after the ATM consumes the session

Session state machine (owned by Authenticator)

pending --approve--> approved --consume--> consumed \ --timeout (60s)--> expired

Non-negotiables

  • QR token TTL: 60 seconds, configurable via env SESSION_TTL_SECONDS.
  • Single-use: a session in any state other than pending rejects approval with HTTP 409.
  • QR token is a signed JWT (HS256). Authenticator verifies signature on approve.
  • Every state change writes to the audit log.

End-of-day check

  1. Pull each other's work.
  2. Run the full flow once: ATM → QR → mobile scan → approve → ATM unlock.
  3. If it breaks, the side that introduced the break fixes it before EOD.

Definition of done for the MVP

  1. Three commands start the system: backend, atm-simulator, mobile-app.
  2. On a phone, the full QR scan → approve → ATM unlock flow takes under 3 seconds.
  3. QR expires automatically at 60 seconds with a clean expired screen.
  4. Audit log shows the full chain of events for at least one successful and one expired session.
  5. A 90-second screen-recorded demo video exists.
  6. The proposal-grade docs (Architecture, API, Run, this Team Split) all exist as PDFs.

What we are NOT trying to do in MVP

  • Integrate with a real ATM vendor (NCR, Diebold) — pilot phase.
  • Integrate with a real bank app SDK — pilot phase.
  • Move money, read balances, or talk to a bank ledger — never.
  • HSM, Redis, Docker, Kubernetes — post-pilot phase.
  • OTP, biometric face match, NFC — v2 features.
